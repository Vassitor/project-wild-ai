# 工程规范与模块边界

更新：2026-10-15。状态：工程规范；P0–P6.5 已按此规范实现，后续阶段继续遵守。库存分层见 [P1 报告](08-p1-implementation.md)，世界分层见 [P2 报告](09-p2-implementation.md)，身体 / 动作分层见 [P3 报告](12-p3-implementation.md)，房主事务见 [P3.5 报告](13-p35-implementation.md)，疾病 / 医疗见 [P4 报告](14-p4-implementation.md)，技能 / 进阶动作 / 陷阱 / 产出分层见 [P5 报告](15-p5-implementation.md)，动物 / 战斗 / 投射 / 观察分层见 [P6 报告](16-p6-implementation.md)，合作租约 / 交付 / 完整日志 / 生命周期分层见 [P6.5 报告](17-p65-implementation.md)。

用户明确要求：代码尽量低耦合、高内聚，并附说明注释。本文约束模块与接口，已确定玩法以 [设计决策](03-design-decisions.md) 为准，具体值以 [配置表](05-initial-balance.md) 为准。

版本 0.2 新增合作模式，[联机设计](06-multiplayer-design.md) 约束会话 / 网络边界。网络隔离在会话和基础设施层，单机与合作复用领域规则。

## 1. 实现原则

- 每个模块围绕一个职责组织，避免一个脚本同时处理背包、疾病、商店与地图。
- 业务规则不依赖 UI 节点路径。UI 提交操作、展示结果，不能直接改货币或身体数值。
- 模块需要的配置、状态和服务由调用方传入；不通过全局单例寻找所有依赖。
- 用明确的方法参数、返回值和局部信号协作。信号适合通知已发生的变化；需要成功 / 失败反馈的命令使用明确返回结果。
- 静态定义与运行状态分离。共享的物品 / 技能 Resource 不能承载某个实例的耐久、数量或位置。
- 合作材料源是显式事务依赖，不写入私人容器；租约、权威 outbox、个人写盘 ACK 和终态去重分别归所属模块处理。
- 个人与完整世界使用完整提交日志；恢复同一提交的实际 JSON 文本，不能用较早的库存备份替代已经确认的收据状态。
- 场景切换交接同一身份 / 档案位置；测试同时显式注入隔离路径并验证交接，不能回退到正式档案。
- `health_rules` 是共享静态子 Resource，身体实例单独保存病程、冷却、迟滞与随机序列。测试修改配置时显式创建 / 复制子 Resource，不能假定外部资源随父配置复制而独立。
- 配方、价格、体力消耗、重量阈值、疾病风险等均可配置；规则只由所属模块实现一次。
- 采用类型标注、稳定 ID 和清晰命名。只在实际出现可复用职责时抽象，不为每个类建立无用途的接口或深继承结构。

## 2. 模块划分

| 模块 | 负责 | 不负责 |
| --- | --- | --- |
| 物品目录 | 静态物品定义与 ID 查询 | 实例数量、耐久、格子位置 |
| 网格库存 | 放置、旋转、堆叠、容量、重量 / 体积统计、事务转移 | 货币扣款、营养恢复、场景展示 |
| 商店服务 | 购买条件、价格、扣款与入仓协调 | 网格碰撞算法 |
| 身体状态 | 血量、营养、水分、体力、健康与疾病数据 | 键盘输入、UI 刷新 |
| 身体规则 | 按输入的时间和行动计算消耗、恢复与状态变化 | 地图节点遍历、直接访问背包 |
| 动作服务 | 前置条件、耗时、体力需求、材料锁定、取消和完成 | 各物品静态定义、所有身体公式 |
| 技能服务 | 经验、点数、前置条件与解锁 | 判断动物寻路、绘制技能面板 |
| 进阶动作 | 捕鱼、制作、升级、维护 / 收取 / 拆除条件与交付 | 档案写入、按键、身体公式 |
| 陷阱规则 | 世界时间检查、匹配实际猎物、饵 / 使用次数 / 捕获状态 | 客户端随机、无动物时虚构掉落 |
| 产出交付 | 实例质量 / 腐坏、自动入包或保留工作点产出 | 技能学习、绘制物品 |
| 世界生成 | 种子、地形与资源数据、连通和出生验证 | 商店、玩家输入、结算奖励 |
| 世界场景 | 根据世界数据实例化显示、碰撞、交互对象 | 定义永久账户规则 |
| 生存模拟协调器 | 统一时间步，协调身体 / 动作 / 世界效果顺序 | 独自实现每个子系统的公式 |
| 任务结算 | 胜负、奖励、随身物资返仓、任务去重 | 网格放置算法、疾病计算 |
| 存档 | 状态编码、版本、恢复与结算记录 | 决定技能是否永久保留 |
| UI | 输入、拖放预览、结果和原因提示 | 第二套库存校验或身体计算 |
| 会话 / 命令入口 | 本地执行或转交房主、身份映射、模式策略、请求 / 结果 | 网格算法、营养公式 |
| 网络适配 | 连接、RPC、快照、实体同步、重连 | 直接决定产出或永久奖励 |

依赖方向为：场景 / UI → 应用服务 → 领域规则与数据。存档负责保存这些状态，不让领域规则主动调用文件写入。

库存发布重量变化，协调器把当前重量作为身体与动作规则的输入；身体模块不直接读取背包节点。动作成功后通知技能服务增加经验，技能模块不轮询每棵树。

## 3. 网格库存契约

采用独立升数体积和宽高占格的双重模型，容器同时检查几何空间与内容容量。重量使用 kg，体积使用 L，坐标使用整数格，旋转只允许 0° / 90°。

静态物品定义：`item_id`、`grid_size`、`unit_weight_kg`、`unit_volume_l`、`max_stack`、类别与用途。可旋转物品使用同一定义，实例记录朝向。

运行实例：`instance_id`、`item_id`、`quantity`、`durability`、`freshness`、可选容器内容。位置由所属容器的放置记录保存，避免实例和容器各保存一套位置而不同步。

容器定义与状态：`container_id`、网格宽高、可接受类别、体积上限、放置记录。角色总负重包含背包、穿戴物和容器内容；穿戴槽也由同一库存服务管理归属与转移。

饮水容器单独记录空重、内部容量和水量：实际重量包含水，背包外部占格 / 占容体积由容器外形决定。不能同时把水的内部体积再加到背包外部占容体积上。

核心操作：

- `can_place`：无副作用，返回越界、重叠、类别、体积或负重问题。
- `try_place` / `try_move` / `try_rotate`：通过完整校验后提交变化。
- `try_split` / `try_merge`：保持总数量、重量和体积守恒；工具 / 容器不堆叠，同品质食物合并保留最早到期时间，拆分继承时间与料理品质。不同营养 / 保质期倍率的食物不能合并，自动产出保持独立堆叠。
- `try_transfer`：先验证源和目标，再原子提交；失败保持双方不变。
- `get_total_weight` / `get_used_volume`：由领域状态计算；界面只显示结果。

预览与提交复用领域校验。拖拽只改预览，不提前删除源物品；网络预览可能过时，最终由房主校验权限 / 版本。旋转坐标统一，确认提交后更新显示。

规则结果返回稳定错误码和必要参数，包括 `OUT_OF_BOUNDS`、`OVERLAP`、`VOLUME_LIMIT`、`WEIGHT_LIMIT`、`INVALID_CATEGORY`、`NO_RESOURCE` 和 `INSUFFICIENT_STAMINA`，由 UI 翻译成中文原因。

## 4. 身体、动作与时间契约

所有规则明确时间单位，模拟统一传入游戏秒 `delta_game_seconds`。游戏秒与现实秒的倍率仅在时钟层换算。身体 / 世界以 60 游戏秒步长推进，关键事件边界拆步；配表中的小时 / 分钟速率只在规则入口换算。

短期体力消耗和长期营养 / 水分消耗分别计算。动作声明体力需求，由统一路径执行扣减；身体周期规则负责基础消耗和恢复，不能对同一动作再次扣相同费用。

睡眠调用相同模拟步，不复制公式。单机 UI 暂停不推进时间，合作个人 UI 不暂停，全员睡眠由房主协调；身体 / 危险事件可中断睡眠和制作。

跨模块条件组合由动作服务协调：读取技能、物品、位置和身体状态，获得校验结果；各模块只决定自身规则。开始时校验并锁定资源，进行中检查持续条件，完成时集中提交产出与经验。

## 5. 注释与说明要求

- 脚本顶部说明职责、主要依赖、哪些状态由它拥有。
- 对公开接口使用 GDScript 文档注释，说明参数单位、返回结果、副作用和失败行为。
- 对网格旋转、堆叠、容量、时间跳过、疾病风险累计、结算去重等关键算法解释原因、边界和约束。
- 对非直观的取舍说明原因，例如为何水的内部体积不再计入背包外部体积。
- 不给每条显而易见的赋值写重复注释；不能用注释代替清晰命名、合理拆分和必要验证。
- 修改行为时同步修改注释与相关说明；未实现部分注明待办与对应阶段，不描述成已实现。

## 6. 验证与交付要求

只为有实际风险的规则编写有价值的测试或自动检查，重点是网格、数量守恒、失败回滚、时间模拟、技能持久化、结算与存档。

库存至少覆盖旋转后越界、复杂重叠、堆叠上限、不同容器转移失败、含水重量与物资守恒。身体至少覆盖缺水、零体力恢复、负重修正，以及实时推进和睡眠使用相同规则。

存档恢复须验证物品 ID、数量、位置、旋转和容量，不能把无效布局静默接受。返仓不足的处理必须持久化，保证读档不丢物资、不再次领奖。

每阶段交付时附简短模块说明、关键接口和验证结果；遇到职责扩散或循环依赖，先调整边界再增加功能。

## 7. 固定技术选择

- 使用 Godot 4.7 系列与类型化 GDScript；P0 实测 4.7.2.stable.official.ed1daf0bf，Compatibility 已迁移并图形验证。
- 配置使用自定义 Resource，运行状态使用独立类型化数据对象，不序列化场景节点引用；数据库按稳定 ID 查询。
- 采用组件 / 组合组织身体、库存与技能，不建立角色 / 工具深继承树；只有主流程、档案和存档等真正跨场景服务使用少量 AutoLoad。
- 信号由所属对象声明，命令同步返回操作结果，不使用一个全局事件总线传递所有业务。
- 存档版本 1，生成器版本 1；存档使用 JSON 完整快照，坐标明确编码，随机种子 / 状态用字符串保留整数精度。
- 单机永久 / 单局同事务，合作房主世界 / 个人档案分离，以任务 / 玩家 / 事件唯一 ID、持久化提交与收据去重，不直接套单文件事务。
- 源码按 `scenes/`、`scripts/domain/`、`scripts/application/`、`scripts/presentation/`、`scripts/infrastructure/`、`data/`、`assets/`、`tests/` 组织；只创建有实际职责的目录和文件。P0 采用代码绘制，无外部美术素材。

## 8. 联机工程约束

- 不硬编码全局唯一 Player，按稳定玩家 ID 获取状态；临时 peer ID 与档案身份分离。
- 单机也通过会话提交意图，房主 / 普通客户端共用命令格式，客户端不直接写权威状态。
- 领域方法同步返回结果，会话可异步返回网络结果；消息已发送不等于事务成功。
- 房主集中推进时钟、随机、AI、伤害和产出；客户端仅预测移动显示，不自行决定库存或奖励。
- 同请求幂等、容器版本、材料 / 占地预留、尸体转移、跨端收据都需验证。
- 网络消息只用稳定 ID 和可序列化基础字段，RPC 留在网络节点，节点路径 / 实体命名稳定。
- 区分公共世界与私人库存同步，背包详情仅本人；新玩家开局后禁加入，原队员恢复原角色。
- 分别验证单机 / 合作暂停、睡眠、死亡、断线、存档和结算；注释说明权威归属、重发和失败恢复。

## 9. P6 动物与战斗边界

动物 / 武器配置、动态实例、AI、命中 / 掉落、恢复校验、显示视图分别组织；攻击只传方向，目标与伤害由权威碰撞决定。武器 / 动物冷却采用现实秒，经配置倍率编码到本局时刻；身体、睡眠和危险事件共用时间入口，提前醒来不能继续消费未模拟的跳时。动物、刷新、个人睡眠和疾病使用独立且可保存的随机流。

近战 / 箭分步碰撞，单个死亡 ID 先标记再交付掉落；捕获与狩猎共用实际动物生命和唯一掉落标记。快照隐藏未来随机序列，足迹按技能开放；UI 插值不修改权威位置。共享 combat_rules Resource 只读，测试调参时显式创建子 Resource，和 health_rules 使用同一约定。


## 10. P7 说明与结算边界

手册、整备检查、倒计时和结果文案只投影配置 / 快照；单机与合作组合根各自应用会话暂停策略。F1 阅读不能执行购物、学习或奖励。长文本使用固定区域滚动，不让自动折行的最小高度把关闭按钮推出视口。

单机与房主共用 WildExpeditionReport 统计个人探索、活动与随身返航数量。明细在清空行装前冻结，与返仓、货币、收据同事务提交；合作交付明细必须与实际 items / reward 相符。旧档案缺少 report 时只显示原总额，不回填编造的历史贡献。测试使用独立档案，控制实验明确区分预置火源 / 位置与正常探索。
